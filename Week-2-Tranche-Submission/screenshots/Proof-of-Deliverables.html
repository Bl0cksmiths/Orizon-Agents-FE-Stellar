SummarySummary · Week-2 delivery

What we shipped in Week 2

This week we shipped the external agent execution path and reputation-gated routing (Deliverable D2), both live on Stellar testnet at orizons.xyz.

External agent execution path — Epic 2

  • Endpoint binding by wallet signature (2.01, 2.05) — an operator attaches their service URL to their on-chain agent by signing a one-time challenge with the wallet that owns it, on its own or inside registration.
  • Signed, bounded dispatch (2.02) — every workflow step sent to an external agent is signed so the operator can verify it came from Orizon; unsafe URLs are refused and every step has a deadline and a size cap.
  • Fair failure rules (2.03) — a step that times out or returns unusable output is not charged and counts against the agent's reputation.
  • Reference agent (2.04) — a public, copyable example agent that runs from its README.
  • Operator dashboard (2.06) — each operator's agents, earnings and reputation in one place, with transaction links.

Reputation-gated routing — Epic 3 · Deliverable D2

  • A reputation floor on every plan (3.01, 3.02) — every planning path reads each agent's on-chain reputation and applies the floor on its conservative lower bound.
  • The trust signal before payment (3.04) — the plan card shows each agent's reputation and its source, the floor applied, and any agent the floor acted on, with the reason.
  • Honest reads (3.03) — if reputation cannot be read from chain, the plan and the card say so.
  • Marketplace standing (3.05) — the floor stated once, on-chain agents marked, standing marks per agent.
  • New agents are hireable on day one (3.06) — a brand-new agent clears the floor by 177 bps, guaranteed by a test and a startup check.
  • Contract addresses kept in agreement (3.07) — checked daily and against the live deployment.
  • On-chain ratings from production — every paid run is rated, and /readiness verifies production is the ledger's authorized scorer.

Fixes and hardening

  • A planning-service outage now returns a fallback plan instead of an error (BLO-121).
  • The floor holds after planning: a step survives only if its agent was offered to the planner.
  • Secrets are masked in every log line; prices show the network's real currency (XLM); accessibility and mobile fixes across the app.

QA — Rie

  • End-to-end QA on testnet of the external execution path (6.05) and the operator surfaces (6.06), a reputation-floor test suite, and 14 defects logged and handed to engineering.

SummarySummary · Stellar integration

Stellar integration this week

All work runs on Stellar testnet.

SDKs and libraries

  • Backend — Python stellar-sdk 13.2.1: builds unsigned XDR for wallets to sign, simulates, prepares and submits Soroban transactions, reads contract storage, verifies SEP-53 message signatures.
  • Frontend — @stellar/stellar-sdk 15.0.1 and @creit.tech/stellar-wallets-kit 2.1.0 for wallet connection and transaction / message signing.
  • Reference agent — verifies Orizon's SEP-53 dispatch signatures with PyNaCl (ed25519) and hand-rolled StrKey decoding, so operators need no Stellar SDK.

Soroban contracts

  • AgentRegistry — owner_of gates endpoint binding; set_active delisting is honoured by routing; register for new agents.
  • ReputationLedger — batched, time-bounded rep_state reads feed the routing floor; submit records ratings; /readiness reads its storage via getLedgerEntries to confirm the authorized scorer.
  • PaymentEscrow — the buyer authorizes a workflow cap from their own wallet; the operator dashboard reads the escrow's on-chain events.
  • AttestationRegistry — sealer role assigned to the production key. Native XLM SAC — the escrow asset.

Wallet integration

  • Binding by signature — the owner wallet signs a SEP-53 challenge naming the agent, endpoint and a nonce; a separately signed message revokes it.
  • Signed dispatch — every step is signed over SEP-53 by a dedicated keypair published as dispatch_signer (GB5MKHDF…KCMR).

Evidence 04Stories 2.01 / 2.05 · Epic 2

Bind an endpoint to an on-chain agent, by wallet signature

The operator endpoint-binding page. An operator enters the id of the agent they registered on-chain and the HTTPS endpoint that runs its work; the registry issues a one-time challenge naming the agent, the endpoint and a nonce, and the wallet that owns the agent signs it — nothing else can authorize the binding. Ownership stays on-chain; the endpoint is an off-chain service record that can be re-bound.

Captured with no wallet connected, so the button reads “connect the owner wallet to sign”. weather_bot and https://agent.example.com/run are the form’s placeholders, not a real binding.
